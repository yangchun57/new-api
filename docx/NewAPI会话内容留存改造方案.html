1结论速览

先给结论，再展开论证。

可行，推荐在 relay 层做一次轻量二开

原生日志面向计费与统计，默认不保存聊天正文。补齐会话留存的最佳做法是：在 relay 中继层拦截请求 messages 与响应 content，写入一张独立的会话记录表。改动集中在后端 4 个包 + 前端 1 个页面，工作量约 3~5 人天，不破坏原生链路。

核心判断：New API 的可插拔中继架构天然适合做这件事——所有模型调用都会经过 relay 层，且请求/响应已经在那里被解析成结构体。我们要做的不是「重写」，而是在一个已知的位置挂一个旁路钩子（hook），把正文旁路落库，主链路零改动。

2现状分析：原生日志记了什么、缺什么

先厘清原生能力边界，才能精准定位"补哪里"。

原生日志已覆盖的内容（计费/统计维度）

New API 的「使用日志」（/usage-logs/common）底层是 logs 表（由 model/log.go 定义），字段面向计费结算与运行统计：

字段含义是否含正文
TokenName / TokenId使用的令牌（API Key）与内部 ID否
ModelName请求的模型标识否
PromptTokens / CompletionTokens输入 / 输出 Token 数否
Quota本次消耗额度否
UseTime请求耗时否
IsStream是否流式响应否
ChannelId / Group渠道与分组否
RequestId / UpstreamRequestId请求链路标识否
Ip客户端 IP（视用户设置）否
Content消息 / 错误描述（非聊天正文）否
OtherJSON：倍率、缓存 Token、模型价格、首字时间等统计信息否

原生日志缺失的内容

  • 用户消息正文（messages[] 里的 content）——默认不落库。
  • AI 完整回复正文（响应里的 content / 流式 delta.content）——默认不落库。
  • 多轮会话关联——一问一答之间没有 conversation_id 串联，难以回溯整段对话。
  • 工具调用 / 函数调用参数（tool_calls）——不在日志维度内。
一个常见误区 日志表里确实有 Content 字段，但它存的是「消息 / 错误描述」，不是聊天正文。因此管理员能确认"这把 Key 在何时调了什么模型、消耗多少"，却看不到对话内容本身。要看到正文，目前只能开 LOGGING_LEVEL=debug 让完整请求/响应进入容器 stdout，再靠日志采集侧去解析——笨重且无法结构化查询。

3需求定义：要留存什么

先明确"留什么、为什么留"，避免过度采集。

留存内容清单

维度字段留存理由
会话正文messages[].content（用户消息）审计、质检、投诉处理、合规举证
响应 content / 流式 delta.content（AI 回复）同上 + 模型输出质量回溯
调用上下文模型、渠道、分组、令牌、RequestId、上游 RequestId、IP、耗时、首字时间把正文与计费/链路数据对齐
会话结构conversation_id + 消息序号 seq串联多轮对话，支持整段回溯
扩展能力tool_calls / function 参数Agent / 工具调用场景的问题排查

典型使用场景

  • 合规审计：内容留存是《生成式人工智能服务管理暂行办法》对服务提供者的要求之一，需要能按用户/时间/令牌回溯。
  • 投诉与争议处理：用户投诉"模型回了不该回的内容"，需要有据可查。
  • 质量质检：抽查真实请求-回复对，评估上游渠道质量与 token 计算准确性。
  • 故障回溯：某条请求报错，希望还原当时的完整上下文（而非仅错误码）。
  • 数据闭环：留存数据可反哺给评测、蒸馏、运营分析。
范围克制原则 留存应遵循「最小必要」：默认只存正文与必要上下文，不存二进制/多模态文件原始字节（除非业务明确需要）；对含敏感信息（手机号、身份证、密钥等）的内容做脱敏或加密。详见第 7 节。

4方案选型：四条路线对比

从"零侵入"到"深度二开"，各有取舍。

方案原理侵入性完整度结构化查询实施成本适用场景
A. debug 日志采集 LOGGING_LEVEL=debug 输出完整请求/响应到容器 stdout，再由日志采集管道（Filebeat/Vector/Loki）解析 无侵入中弱（需自行解析日志）低 临时排查、已有成熟日志中台
B. relay 层拦截落库 在中继层挂旁路钩子，解析 messages 与响应 content，写入独立会话表 改源码高强（独立表 + 索引）中 长期留存、需要结构化检索
C. 扩展原生 Log 模型 复用 logs 表，把正文塞进新增字段或 Other JSON 改源码中中（字段冗余、检索弱）中低 快速起步、对查询要求不高
D. 旁路代理录制 在 New API 之前加一层反向代理 / sidecar（自研或 mitmproxy/eBPF），复制流量并录制正文 无侵入高强（独立存储）高 不动源码、多网关通用、且需解密 TLS

5推荐方案详解：relay 层拦截落库

核心思路：在中继层挂一个旁路钩子，主链路零改动。

整体数据流

  1. 客户端请求 /v1/chat/completions → 经鉴权中间件 → 进入 relay 中继层。
  2. 在 relay 解析出 OpenAI 结构体的 ChatRequest.Messages 后，挂钩子提取用户消息正文（此时尚未请求上游）。
  3. 中继正常请求上游渠道，拿到响应。
  4. 在响应处理阶段（DoResponse / 流式 DoStreamResponse），挂钩子提取 AI 回复正文：非流式直接读 choices[0].message.content；流式则把每个 delta.content 片段拼接。
  5. 请求结束后，把「用户消息 + AI 回复 + 上下文」异步写入独立会话表（不阻塞主响应）。

关键改动点（后端 4 包 + 前端 1 页）

位置改动内容说明
model/chat_log.go新增 ChatLog 模型 + 建表迁移 + RecordChatLog()数据层，核心新增文件
relay/relay_chat.go请求入口提取 messages；响应出口提取 content挂旁路钩子，主链路不变

难点：流式响应的正文拼接

流式（SSE）场景下，AI 回复被拆成多个 data: 片段，每段只带一小节 delta.content。留存完整回复，需要在流的出口把这些片段按顺序拼接：

// 伪代码：在 DoStreamResponse 出口收集 delta.content
var sb strings.Builder
for {
    chunk, err := stream.Recv()          // 从上游 SSE 流读取一个片段
    if err == io.EOF { break }

    // 原始透传给客户端（不打断主链路）
    c.Writer.WriteString(chunk)

    // 旁路：只解析 JSON，提取 delta.content 做拼接
    var piece struct {
        Choices []struct {
            Delta struct {
                Content *string `json:"content"`
            } `json:"delta"`
        } `json:"choices"`
    }
    if json.Unmarshal(chunk, &piece) == nil {
        if piece.Choices[0].Delta.Content != nil {
            sb.WriteString(*piece.Choices[0].Delta.Content)
        }
    }
}
fullReply := sb.String()   // 拼接得到的完整回复
拼接要点 流式收集与透传要解耦：透传走原逻辑保证性能与顺序，收集只做 JSON 解析 + 字符串追加，二者互不阻塞；最后在请求结束后一次性写库，避免每条流都触发多次 DB 写入。

异步写库，避免拖慢主链路

正文落库应是旁路异步操作：用一个带缓冲的 channel + 独立 goroutine（或复用 New API 已有的异步任务机制）批量写库，失败只记错误日志、不回滚主请求。

// 伪代码：异步旁路写库
func HookRecord(c *gin.Context, req *ChatRequest, reply string, meta *Meta) {
    if !common.ChatLogEnabled { return }

    logCh <- &ChatLog{
        UserId:            c.GetInt("id"),
        TokenName:         c.GetString("token_name"),
        ModelName:         req.Model,
        RequestId:         c.GetString("request_id"),
        UpstreamRequestId: meta.UpstreamRequestId,
        Messages:          req.Messages,      // 用户消息
        Reply:             reply,             // AI 完整回复
        PromptTokens:      meta.PromptTokens,
        CompletionTokens:  meta.CompletionTokens,
        IsStream:          meta.IsStream,
        CreatedAt:         time.Now().Unix(),
    }
}

// 后台 worker
for rec := range logCh { model.RecordChatLog(rec) }

6数据模型设计

推荐「消息级单表 + conversation_id」结构，兼顾检索与容量。

表结构：chat_logs

// model/chat_log.go
type ChatLog struct {
    Id                int    `gorm:"primaryKey;autoIncrement" json:"id"`
    UserId            int    `gorm:"index" json:"user_id"`
    TokenName         string `gorm:"index" json:"token_name"`
    ModelName         string `gorm:"index" json:"model_name"`
    ChannelId         int    `json:"channel_id"`
    Group             string `json:"group"`
    RequestId         string `gorm:"index" json:"request_id"`
    UpstreamRequestId string `json:"upstream_request_id"`
    ConversationId    string `gorm:"index" json:"conversation_id"` // 串联多轮
    Seq               int    `json:"seq"`                           // 消息序号
    Role              string `json:"role"`                          // user / assistant / tool
    Content           string `gorm:"type:text" json:"content"`      // 正文（可加密/脱敏）
    PromptTokens      int    `json:"prompt_tokens"`
    CompletionTokens  int    `json:"completion_tokens"`
    Quota             int    `json:"quota"`
    IsStream          bool   `json:"is_stream"`
    Status            int    `json:"status"`                        // 1 成功 2 失败
    LatencyMs         int    `json:"latency_ms"`
    Ip                string `json:"ip"`
    CreatedAt         int64  `gorm:"index" json:"created_at"`
}

索引设计

索引用途
(UserId, CreatedAt)按用户 + 时间回溯（最常见查询）
(TokenName, CreatedAt)按令牌追溯
RequestId对齐原生日志，一次请求查全部消息
(ConversationId, Seq)整段多轮对话还原

为什么用「消息级」而非「会话级单行」

  • 检索友好：可直接按 role、关键词、时间范围过滤单条消息。
  • 容量可控：长对话拆成多行，避免单条 text 字段膨胀导致的大字段查询慢。
  • 兼容流式：流式回复拼完后作为一条 assistant 记录写入，与用户消息天然对齐。
  • 可扩展：后续要加 tool_calls、多模态 URL 等，只需加字段，不动表结构主键。
存储引擎选择 日志量大时，会话表可复用 New API 的 LOG_SQL_DSN 独立库机制：小规模用 SQLite/PostgreSQL，中大规模用 MySQL，海量且需长期归档时切 ClickHouse（New API 已内置 ClickHouse 日志支持，且支持 LOG_SQL_CLICKHOUSE_TTL_DAYS 自动过期）。

7隐私与合规

正文比元数据敏感得多，合规是硬门槛。

必须处理的三个层面

层面要求落地手段
访问控制正文仅管理员可见，普通用户只能查自己的记录复用 formatUserLogs 的权限过滤思路，剥离渠道/上游等敏感字段
数据加密落库正文加密存储，防拖库泄密Content 字段用 AES-256-GCM 加密，密钥由 CHAT_LOG_ENC_KEY 注入，不入库
脱敏敏感信息（手机号、身份证、密钥、Token）写入前脱敏正则脱敏 + 可配置规则；高敏字段不落库
知情与授权用户知情 + 可选关闭提供 opt-in/opt-out 开关，尊重用户选择
留存期限满足最小必要，过期自动清理设置 CHAT_LOG_RETENTION_DAYS，超期定时删除或走 ClickHouse TTL

合规红线

  • 《生成式人工智能服务管理暂行办法》：要求服务提供者对用户输入和生成内容依法留存、配合监管检查。
  • 《个人信息保护法》（PIPL）：正文可能含个人信息，采集需有合法依据，需告知用户并保障删除权。
  • 《数据安全法》：涉及重要数据/核心数据时需分级分类保护，跨境需评估。
  • 若面向公众提供服务且未经备案，需遵守「不向中国地区公众提供未经备案的生成式 AI 服务」的红线。
给运营者的建议 留存能力上线前，务必先完成隐私政策更新 + 用户告知 + 留存期限与删除机制三件事，再谈技术实现。技术方案本身不解决合规，只提供合规所需的"能力"。

8存储容量与性能

正文留存最直接的代价是存储与写入压力，需提前估算。

容量估算模型

假设取值
日均请求量10 万次
平均单次正文量（用户消息 + AI 回复）约 4 KB（≈ 2000 中文字符）
日均新增约 400 MB
月均 / 年均约 12 GB / 146 GB

控本策略

  • 阈值裁剪：超过 CHAT_LOG_MAX_BODY_KB（如 64 KB）的正文只存摘要或截断，防大字段。
  • 压缩：正文做 gzip/zstd 压缩后存储（文本压缩率通常 3~5 倍）。
  • 冷热分离：近期热数据留主库，超期归档到对象存储（S3/OSS）或 ClickHouse。
  • 定时清理：按 CHAT_LOG_RETENTION_DAYS 滚动删除，配合 ClickHouse TTL 自动化。
  • 分库分表：海量场景按 UserId 或时间分片，避免单表过大。

9风险与对策

正文留存是把双刃剑，风险要前置识别。

风险影响对策
数据泄露（拖库）高正文加密存储、密钥独立管理、库权限最小化

11存储优化：文件系统 + 上下文去重

两项正交优化：换存储介质解决"存在哪、多便宜"，去重解决"存多少"。二者叠加收益最大。

为什么必须去重：O(n²) 陷阱

OpenAI Chat Completions API 是无状态的——服务端不保存会话，客户端每轮都必须把完整历史 messages 重发一遍：

  • 第 1 轮：[user] → 1 条历史 + 1 条回复 = 2 条
  • 第 2 轮：[user, asst, user] → 3 条历史 + 1 条回复 = 4 条
  • 第 k 轮：2k-1 条历史 + 1 条回复 = 2k 条

每轮都完整落库，n 轮对话总存储量为 n(n+1) 条，是二次增长。去重后只存增量，每轮固定 2 条，总量 2n 条。

对话轮数全量存储去重后节省率 = (n−1)/(n+1)
10 轮110 条20 条81.8%
20 轮420 条40 条90.5%
50 轮2550 条100 条96.1%
结论 去重不只是"可以"，而是长对话场景下的必需优化。对话越长收益越大；若历史含图片 base64 或多模态内容，节省的字节量还要再放大一个量级（这也是长对话 token 账单昂贵的原因）。

去重的三种实现路径

路径原理前置条件推荐度
内容哈希去重 对每条 message 算 hash(user_id + role + content)，已存在的 hash 只存引用、不存正文 无（通用） 高
前缀增量 多轮历史构成严格前缀序列，比对上一轮基线后只存 messages[baseLen:] 需 conversation_id 或前缀可推断 最高
message_id 关联 请求体带每条消息的稳定 ID（OpenAI Responses API 的 item_id 或自定义扩展） 客户端必须配合改造 中

核心实现：前缀增量 + 失配降级

// 伪代码：基于前缀比对的增量提取
func diffMessages(convID string, msgs []Message) (增量 []Message, baseLen int) {
    base := getBaseline(convID)   // 上一轮基线 hash 列表（缓存/DB）

    // 1) 前缀校验：历史是否严格追加
    for i, h := range base {
        if i >= len(msgs) || hash(msgs[i]) != h {
            // 前缀失配：用户编辑了历史 / 上下文被截断
            // → 退化为全量存，并重置基线
            return msgs, 0
        }
    }
    // 2) 前缀一致，仅返回新增的尾部消息
    return msgs[len(base):], len(base)
}
关键前提：conversation_id 从哪来？ Chat Completions API 没有标准的 conversation_id 字段，这是去重的先决问题。推荐三层降级策略：
① 最优：客户端在 Header 或请求体中带 X-Conversation-Id（或走 Responses API 的 conversation 参数）；
② 次优：服务端用「内容前缀匹配」启发式推断——若本次 messages 前缀 == 上次 messages + 上次回复，则判为同一对话延续；
③ 兜底：都识别不出时存全量，不做去重。

存储介质：索引与正文分离

正文是典型的大文本字段，全塞进数据库性价比很低（表膨胀、索引膨胀、备份慢）。业界标准做法是混合架构：

层存什么载体
元数据索引user_id、时间、模型、token 数、conversation_id、文件路径 + offset + 长度MySQL / PostgreSQL
正文内容去重后的增量消息正文（压缩）对象存储（MinIO / S3 / OSS / COS）

检索链路：SQL 查索引 → 得到路径与 offset → Range Read 读回正文 → 按 seq 重组对话。

多节点部署的陷阱 New API 支持多节点部署（NODE_NAME）。若用本地磁盘，每个节点各存各的，检索时必须跨节点聚合，运维成本高。因此正文存储必须走对象存储；本地磁盘仅适合单机验证或 P0 原型。

文件组织规范

  • 格式：JSONL（每行一条记录）——追加友好、可按行流式读取、天然支持按 offset 定位。
  • 分片：按 日期 / user_id 分目录，例如 chat-logs/2026/09/03/user-123/part-0001.jsonl.gz。
  • 压缩：gzip / zstd 打包（中文本压缩率通常 3~5 倍）。
  • 攒批：按 (user_id, 时间窗口) 缓冲，攒够 N 条或 T 秒再打包——避免海量小文件（inode 压力 + 对象存储请求成本）。
  • 生命周期：直接复用对象存储的 Lifecycle 策略做自动过期，比数据库定时任务更省心。
不要用 Parquet 做实时写入 Parquet 列存压缩率更高、适合分析，但不支持追加写，只适合批处理归档层。实时写入层用 JSONL，归档分析层再转 Parquet。

组合后的最终架构

[relay 层钩子]
      ↓  提取 messages + 响应 content
[去重器]  算 hash / 比对基线 / 只输出增量（失配则全量）
      ↓  增量消息
[本地缓冲队列]  按 (user_id, 时间窗口) 攒批
      ↓  攒够 N 条或 T 秒
[打包压缩]  写 JSONL + gzip/zstd
      ↓
[对象存储]  s3://bucket/chat-logs/2026/09/03/user-123/part-xxx.jsonl.gz
      ↓  同时写入
[数据库索引]  user_id | conversation_id | 文件路径 | offset | 长度 | 时间 | 模型 | token

新增风险与对策

风险影响对策
增量丢失导致对话残缺 高 定期全量快照：每 N 轮或每 M 条强制存一次完整基线，损坏时从最近快照恢复
前缀失配（编辑历史 / 上下文截断） 中 前缀校验失败即降级为全量存，并重置基线（见上方伪代码）
客户端自行维护上下文、只发增量 中 去重器识别"非追加式"请求，对该客户端直接存全量
索引与文件不一致（写了索引但文件失败） 中 先写文件成功再写索引；定期巡检孤儿索引与游离文件
小文件泛滥 中 强制攒批打包，单文件控制在 16~64 MB 量级
两项优化建议一并纳入 P1 阶段

去重主要改 relay 层钩子（加一个 diff 步骤），存储切换主要改落库层（DB 写索引 + 对象存储写正文），二者互不耦合、可分步实施。若时间紧张，优先做去重——它把存储量从 O(n²) 降到 O(n)，比换介质省钱更直接；介质切换可留到数据量真正上来之后再补。

12存储选型：数据库与检索架构

基于两个前置约束给出结论：规模刚起步（日请求量未定）+ 全文检索是核心功能。

先点破一个矛盾

对象存储里的正文无法被检索 第 11 章建议的「正文放对象存储」是以"检索需求弱"为前提的。既然检索是核心功能，正文就必须有一份落在可检索的存储中——对象存储的角色应从"主存"降级为"归档层"。

好消息：起步阶段去重+压缩后一年仅约 8 GB，正文直接存数据库完全扛得住，根本不需要对象存储层。少一层，就少一整套一致性、小文件、跨节点聚合的麻烦。

两条实施路径

路径组成优势局限
A. 极简起步 MySQL 8.0 单实例，正文存 TEXT 字段，ngram FULLTEXT 检索 零额外组件，一天跑通 检索体验基础（无高亮、相关性弱）
B. 检索优先 MySQL 存元数据+正文（主存储） + Meilisearch 索引正文（检索层），异步队列双写 毫秒级检索、高亮、容错、相关性排序好 多一个轻量组件（约 200 MB 内存）
推荐节奏 既然检索是核心功能，最终应走路径 B。但建议先用路径 A 跑通最小闭环（验证去重链路与数据正确性），再叠加 Meilisearch——不要同时引入"去重"和"检索引擎"两个新变量，出问题难以定位。

索引粒度的设计选择

  • 按消息粒度索引：命中精准，能定位到具体哪句话 —— 推荐。
  • 按会话粒度索引：能看到完整上下文，但命中模糊、返回体大。
  • 最佳实践：按消息粒度索引，返回时通过 conversation_id 带上上下文（前后各 N 条）。兼顾精准与可读性。

注意：去重不影响检索。去重只改变存储方式；检索时按 conversation_id 重组出完整对话后再写入索引，二者正交。
